Installation de pfSense

Installation et configuration de pfSense​

Dans ce chapitre, nous allons installer pfSense, un pare-feu et routeur open source basé sur FreeBSD. L'installation peut être réalisée sur un ordinateur physique ou dans une machine virtuelle telle que VirtualBox.

L'image ISO officielle de pfSense peut être téléchargée depuis le dépôt suivant :

https://repo.ialab.dsu.edu/pfsense/

Prérequis matériels (installation sur une machine physique)​

Avant de commencer l'installation, assurez-vous de disposer des éléments suivants :

  • Un ordinateur compatible avec une architecture 64 bits.
  • 2 Go de mémoire RAM minimum (4 Go recommandés).
  • 8 Go d'espace disque minimum.
  • Deux interfaces réseau :
    • WAN : connexion vers Internet.
    • LAN : connexion vers le réseau local.
  • Une clé USB bootable d'au moins 4 Go contenant l'image ISO de pfSense.

Prérequis pour une installation sous VirtualBox​

Si vous souhaitez installer pfSense dans une machine virtuelle, les prérequis sont les suivants :

  • Installer Oracle VirtualBox sur votre ordinateur.
  • Télécharger l'image ISO de pfSense.
  • Créer une nouvelle machine virtuelle.
  • Monter l'image ISO de pfSense dans le lecteur optique virtuel.
  • Configurer les paramètres de la machine virtuelle.

Configuration d'un Proxy (HAProxy)​

Dans une architecture réseau, il est déconseillé d'exposer directement un serveur interne (serveur Web, application, etc.) sur Internet. Une meilleure approche consiste à utiliser un proxy inverse (Reverse Proxy).

Le proxy reçoit toutes les requêtes des clients, puis les transmet au serveur interne. Ainsi, les utilisateurs ne communiquent jamais directement avec le serveur final.

Pourquoi utiliser un proxy ?​

L'utilisation d'un proxy inverse présente plusieurs avantages :

  • Masquer l'adresse IP du serveur final : les clients voient uniquement l'adresse IP de pfSense, jamais celle du serveur interne.
  • Renforcer la sécurité : le serveur est isolé du réseau public et ne reçoit pas directement les connexions provenant d'Internet.
  • Centraliser les accès : plusieurs serveurs peuvent être publiés derrière une seule adresse IP publique.
  • Terminer les connexions HTTPS (SSL Offloading) : le proxy peut gérer les certificats SSL/TLS à la place des serveurs.
  • Répartir la charge (Load Balancing) entre plusieurs serveurs.
  • Filtrer le trafic avant qu'il n'atteigne les serveurs internes.

Principe de fonctionnement​

                Internet
                    │
                    ▼
             Adresse IP Publique
                    │
              +-------------+
              |   pfSense   |
              |   HAProxy   |
              +-------------+
                     │
                     │
                     ▼
               Serveur FTP/SSH
                 10.10.10.12

Dans cette architecture :

  1. Le client envoie une requête vers l'adresse IP publique de pfSense.
  2. Le NAT redirige la connexion vers le proxy HAProxy.
  3. HAProxy analyse la requête (nom de domaine, port, protocole...).
  4. Il transmet ensuite la requête au serveur approprié.
  5. Le serveur répond à HAProxy.
  6. HAProxy renvoie la réponse au client.

Le client ne connaît jamais l'adresse IP privée des serveurs internes.

Configuration des règles NAT​

Pour que les connexions provenant d'Internet atteignent le proxy, il est nécessaire de créer une règle de NAT Port Forward.

Le principe est le suivant :

  • les connexions arrivant sur les ports 80 (HTTP) ou 443 (HTTPS) de l'adresse IP publique de pfSense ;
  • sont redirigées vers le service HAProxy ;
  • HAProxy décide ensuite vers quel serveur interne envoyer la requête.

  • Le proxy contrôle l'ensemble des connexions avant qu'elles n'atteignent les serveurs.
  • L'infrastructure devient plus sécurisée, évolutive et facile à administrer.

DMZ (Demilitarized Zone)​

Une DMZ (Demilitarized Zone) est un sous-réseau placé entre le réseau interne (LAN) et Internet (WAN). Elle est destinée à héberger les services qui doivent être accessibles depuis l'extérieur, tels que :

  • Serveur Web (Apache, Nginx)
  • Serveur FTP
  • Serveur de messagerie
  • Serveur DNS public
  • Serveur Proxy

L'objectif principal d'une DMZ est de protéger le réseau interne tout en permettant aux utilisateurs externes d'accéder aux services publics.

Architecture​

                  Internet (WAN)
                         │
                         │
                Adresse IP publique
                         │
                  +---------------+
                  |    pfSense    |
                  +---------------+
                  │               │
          LAN     │               │      DMZ
    10.10.10.0/24 │               │ 20.20.20.0/24
                  │               │
          PC Utilisateur       Serveur Web
                                 Apache

Règles de sécurité​

DMZ → WAN​

Les machines situées dans la DMZ doivent pouvoir accéder à Internet afin de :

  • installer des mises à jour ;
  • télécharger des paquets ;
  • synchroniser l'heure (NTP) ;
  • récupérer des certificats SSL ;
  • communiquer avec des services externes.

Une règle autorisant le trafic DMZ → WAN est donc nécessaire.

DMZ → LAN​

Le trafic provenant de la DMZ vers le LAN doit être strictement limité, voire totalement interdit.

Pourquoi ?

Les serveurs hébergés dans la DMZ sont exposés à Internet et représentent les premières cibles potentielles des attaques.

Si un attaquant compromet un serveur Web placé dans la DMZ, il pourrait tenter de rebondir vers le réseau interne afin de :

  • voler des données sensibles ;
  • compromettre les postes utilisateurs ;
  • attaquer les serveurs internes ;
  • propager un logiciel malveillant.

Pour cette raison, la politique de sécurité recommandée est :

  • ✅ WAN → DMZ : autorisé uniquement sur les services publiés (HTTP, HTTPS, etc.).
  • ✅ DMZ → WAN : autorisé.
  • ❌ DMZ → LAN : interdit, sauf exception explicitement autorisée.
  • ❌ WAN → LAN : interdit.

Résultat​

Après cette configuration :

  • Les utilisateurs d'Internet peuvent accéder au serveur Web de la DMZ.
  • Le serveur Web peut accéder à Internet pour ses mises à jour.
  • Les machines de la DMZ ne peuvent pas accéder au réseau LAN.
  • Le réseau interne reste isolé et protégé, même si un serveur de la DMZ est compromis.

Cette architecture est largement utilisée en entreprise pour publier des services accessibles depuis Internet tout en limitant les risques pour le réseau interne.

Proxy Squid​

Squid est un serveur proxy et un proxy de mise en cache (cache proxy) largement utilisé dans les entreprises. Il permet de contrôler l'accès à Internet, d'améliorer les performances de navigation et de renforcer la sécurité du réseau.

Grâce à Squid, les postes clients n'accèdent plus directement aux sites Internet. Toutes les requêtes HTTP et HTTPS transitent par le proxy, qui peut :

  • Autoriser ou refuser l'accès à certains sites.
  • Mettre en cache les pages Web afin d'accélérer la navigation.
  • Réduire la consommation de bande passante.
  • Enregistrer les connexions des utilisateurs.
  • Appliquer des politiques de sécurité.

Architecture​

                 Internet
                     │
                     ▼
              +---------------+
              |    pfSense    |
              |     Squid     |
              +---------------+
                     │
        -----------------------------
        │             │             │
      Client 1     Client 2     Client 3

Toutes les connexions Web passent par le proxy Squid avant d'être envoyées vers Internet.

Packages utilisés​

Cette configuration repose sur trois packages complémentaires.

Squid​

Le package Squid fournit le serveur proxy qui intercepte et traite les connexions Web.

Ses principales fonctionnalités sont :

  • Proxy HTTP/HTTPS
  • Cache Web
  • Authentification des utilisateurs
  • Journalisation des connexions
  • Contrôle d'accès

SquidGuard​

SquidGuard est un module de filtrage qui fonctionne avec Squid.

Il permet notamment de :

  • Bloquer des catégories de sites Internet.
  • Autoriser uniquement certains domaines.
  • Créer des listes blanches (Whitelist).
  • Créer des listes noires (Blacklist).
  • Filtrer les accès selon les utilisateurs ou les groupes.

Lightsquid​

Lightsquid est un outil d'analyse des journaux de Squid.

Il génère des rapports détaillés sur :

  • les sites consultés ;
  • le volume de données échangées ;
  • les utilisateurs ;
  • les horaires de connexion ;
  • les statistiques de navigation.

OpenVPN

OpenVPN est un logiciel de réseau privé virtuel (VPN) open source qui permet de créer des connexions sécurisées entre des réseaux distants. C’est un VPN SSL intégral qui met en œuvre une extension réseau sécurisée de niveau 2 ou 3 OSI grâce au protocole standard du secteur SSL/TLS. Il supporte des méthodes d'authentification client variées basées sur des certificats, des cartes à puce et/ou des identifiants utilisateur/mot de passe, tout en permettant des politiques d'accès spécifiques à l'utilisateur ou au groupe via l'application de règles de pare-feu sur l'interface VPN virtuelle. OpenVPN n'agit pas en tant que proxy d'application web et ne fonctionne pas par le biais d'un navigateur internet.

https://openvpn.net/community-resources/how-to/

OpenVPN prend en charge plusieurs types de connexions :​

VPN Site-to-Site​

Un VPN site à site est une connexion entre deux ou plusieurs réseaux. Interconnecter deux entités via un VPN afin qu'elles puissent partager leurs ressources comme si elles étaient sur le même réseau, alors c'est bien un VPN site-to-site.

VPN Point-à-Point (P2P VPN​

Un réseau privé virtuel (P2P) est un type de VPN compatible avec un réseau peer-to-peer. Un réseau peer-to-peer permet aux utilisateurs de transmettre et de recevoir des données sur le réseau via plusieurs nœuds plutôt qu'à un seul endroit, car chaque membre ou pair agit comme un point de connexion potentiel. Elle connecte deux appareils directement via un tunnel sécurisé. Utilisé pour connecter deux serveurs, ordinateurs ou équipements IoT. Plus simple qu’un VPN site-to-site, mais limité à deux machines. Exemple : Un serveur A envoie des données chiffrées à un serveur B.

VPN d'Accès à Distance (Remote Access VPN)​

Le VPN d'accès à distance garantit que les connexions entre les réseaux d'entreprise et les appareils distants et mobiles sont sécurisées, et peuvent être accessibles pratiquement partout où se trouvent les utilisateurs

La gestion des certificats

Nous devons créer une autorité de certification interne sur le firewall PfSense, puis nous allons créer un certificat dédié au serveur. Ce certificat sera utilisé pour sécuriser notre tunnel VPN.

Créer l'autorité de certification​

Pour créer l'autorité de certification sur pfSense (si vous n'en avez pas déjà une), vous devez accéder au menu : System > Cert. Manager

Dans l'onglet "Authorities", cliquez sur le bouton "Add".

Créer le certificat Server​

Nous allons créer un certificat de type "Server" en nous basant sur notre nouvelle autorité de certification. Toujours dans "Certificate Manager", cette fois-ci dans l'onglet "Certificates", cliquez sur le bouton "Add".

Choisissez la méthode "Create an Internal Certificate" nom (VPN_ACC) et sélectionnez l'autorité de certification au niveau du paramètre "Certificate authority".

Par défaut, la validité du certificat est fixée à 3650 jours soit 10 ans. Le "Common Name" correspond là aussi au nom intégré dans le certificat, si vous souhaitez établir une connexion VPN basée sur un nom de domaine, il est préférable d'indiquer cette valeur ici.

On choisit le type de certificat (Certificate Type) suivant : Server Certificate. Puis Save pour sauvegarder

La partie certificat est terminée, passons à la suite.

Configurer le serveur OpenVPN​

Maintenant que la partie certificat est opérationnelle et que nous disposons d'un compte utilisateur, on peut s'attaquer à la configuration du VPN.

Cliquez sur le menu "VPN" puis "OpenVPN"

Dans l'onglet "Servers", cliquez sur "Add" pour créer une nouvelle configuration.

La première chose à faire, c'est de choisir le "Server Mode" suivant :

Remote Access (SSL/TLS + User Auth).

Pour le VPN, le protocole s'appuie sur de l'UDP, avec le port 1194 par défaut. Pour l'interface, nous allons conserver "WAN" puisque c'est bien par cette interface que l'on va se connecter en accès distant.

Au niveau de la partie chiffrement, un peu plus bas dans la page, nous allons sélectionner notre autorité de certification au niveau du champ "Peer Certificate Authority". En complément, sélectionnez le certificat Server au niveau du champ "Server certificate".

Pour l'algorithme de chiffrement (Encryption Algorithm), nous allons choisir l'AES-256-CBC. La sécurité sera renforcée, mais cela impact légèrement les performances, car le processus de chiffrement est alourdi : il sera toujours possible de modifier cette valeur. Il n'est pas nécessaire de modifier les autres options liées au chiffrement.

Passons maintenant à la configuration de notre tunnel VPN en lui-même.

  • IPv4 Tunnel Network : adresse du réseau VPN, c'est-à-dire que lorsqu'un client va se connecter en VPN il obtiendra une adresse IP dans ce réseau au niveau de la carte réseau locale du PC

  • Redirect IPv4 Gateway : si vous cochez cette option, vous passez sur un full tunnel c'est-à-dire que tous les flux réseau du PC distant vont passer dans le VPN, sinon nous sommes en split-tunnel

  • IPv4 Local network : les adresses réseau des LAN que vous souhaitez rendre accessibles via ce tunnel VPN. Dans mon exemple, je souhaite rendre accessible le réseau 10.10.10.0/24 via le VPN. Si vous avez plusieurs valeurs à indiquer, il faut les séparer par une virgule

  • Concurrent connections : le nombre de connexions VPN simultanés que vous autorisez.

Si vous avez besoin de plus de 60 connexions VPN en simultanés, vous ne devez pas utiliser un réseau VPN en /24, mais vous devez prendre plus large. Dans ce cas, modifiez la valeur "IPv4 Tunnel Network" définie précédemment.

Descendez dans la page... On s'approche de la fin. Dans la zone "Custom options", indiquez : auth-nocache. Cette option offre une protection supplémentaire contre le vol des identifiants en refusant la mise en cache.

Créer les règles de firewall pour OpenVPN

D'une part, nous devons créer une règle pour autoriser les clients à monter la connexion VPN, et d'autre part nous devons créer une ou plusieurs règles pour autoriser l'accès aux ressources : serveur en RDP, serveur de fichiers, application web, etc.

Autoriser le flux OpenVPN​

Cliquez sur le menu "Firewall" > "WAN". Il est nécessaire de créer une nouvelle règle pour l'interface WAN, en sélectionnant le protocole UDP.

Validez la création de la règle et appliquez la configuration.

À partir de ce moment-là, il est possible de monter le tunnel VPN sur un PC, mais les ressources de votre entreprise seront inaccessibles.

Autoriser les flux vers les ressources​

La règle qui suit sert à autoriser l'accès en RDP à l'hôte 10.10.10.20 (qui fait bien parti du réseau autorisé dans la configuration du VPN) au travers du tunnel VPN. Vous devez créer une ou plusieurs règles en fonction des ressources auxquelles vos utilisateurs doivent accéder via le VPN, en limitant les flux au maximum.

Pour la destination, ce sera donc mon hôte et le port 3389 pour le RDP. De la même façon que pour la règle précédente, indiquez une description et activez la journalisation si vous le souhaitez.

La configuration est terminée... Il ne reste plus qu'à tester !
